# Deposits — collecting money from a customer

A deposit moves funds from the customer's mobile money wallet into the merchant's pawaPay wallet. The merchant initiates it; the customer authorises it on their phone (PIN prompt, OTP, or redirect, depending on the provider).

## Endpoints

| Method | Path                                       | Purpose                              | Signed? |
|--------|--------------------------------------------|--------------------------------------|---------|
| POST   | `/v2/deposits`                             | Initiate a deposit                   | Yes     |
| GET    | `/v2/deposits/{depositId}`                 | Check status                         | No      |
| POST   | `/v2/deposits/resend-callback/{depositId}` | Re-trigger the final-state callback  | No      |

## State machine

```
ACCEPTED → PROCESSING → (IN_RECONCILIATION) → COMPLETED | FAILED
```

Initiation response status: `ACCEPTED | REJECTED | DUPLICATE_IGNORED`.
Lifecycle status (in status-check `data.status`): `ACCEPTED, PROCESSING, IN_RECONCILIATION, COMPLETED, FAILED`.
Callback status: `COMPLETED, PROCESSING, FAILED` only (PROCESSING in callbacks happens for REDIRECT_AUTH providers — see below).

Terminal: `COMPLETED`, `FAILED`. `IN_RECONCILIATION` is automatic — no action needed; pawaPay's reconciler resolves it within minutes (sometimes longer for failures).

## Initiate — POST /v2/deposits

### Request

```json
{
  "depositId": "afb57b93-7849-49aa-babb-4c3ccbfe3d79",
  "amount": "100",
  "currency": "RWF",
  "payer": {
    "type": "MMO",
    "accountDetails": {
      "phoneNumber": "250783456789",
      "provider": "MTN_MOMO_RWA"
    }
  },
  "customerMessage": "Order 12345",
  "clientReferenceId": "ORD-12345",
  "preAuthorisationCode": "367025",
  "successfulUrl": "https://merchant.com/payment/success",
  "failedUrl": "https://merchant.com/payment/failed",
  "metadata": [
    { "orderId": "ORD-12345" },
    { "customerId": "customer@email.com", "isPII": true }
  ]
}
```

Field reference:

- `depositId` (required) — UUIDv4 string, generated by merchant. Idempotency key. Persist before calling.
- `amount` (required) — string. Pattern `^([0]|([1-9][0-9]{0,17}))([.][0-9]{0,3}[1-9])?$`. Use the provider's `decimalsInAmount` to decide rounding.
- `currency` (required) — ISO 4217, e.g. `"RWF"`, `"ZMW"`, `"XOF"`.
- `payer.type` (required) — only `"MMO"` supported in v2.
- `payer.accountDetails.phoneNumber` (required) — MSISDN, digits only, full country code, no `+`, no spaces. Run through `predict-provider` first.
- `payer.accountDetails.provider` (required) — provider code, e.g. `"MTN_MOMO_RWA"`. Get list from `active-conf` or use `predict-provider` output.
- `customerMessage` (optional) — 4-22 chars, `[a-zA-Z0-9 ]`. SMS narration the customer sees on receipt. Defaults to your company name if omitted.
- `clientReferenceId` (optional) — your reference (invoice ID, order ID). Returned in status-check response (NOT in callbacks).
- `preAuthorisationCode` (conditional) — required ONLY when the provider's `authType = PREAUTH` (currently Orange Burkina Faso). Customer must generate this OTP first via their MMO USSD menu.
- `successfulUrl` / `failedUrl` (conditional) — required ONLY when the provider's `authType = REDIRECT_AUTH` (currently Wave Senegal and Wave Ivory Coast). Customer is redirected to these after completing/failing the payment.
- `metadata` (optional) — array of single-key objects. Up to 10 entries. Set `"isPII": true` on the same object to flag GDPR-sensitive entries. Returned as a flat object on responses.

### Response — 200

```json
{
  "depositId": "afb57b93-7849-49aa-babb-4c3ccbfe3d79",
  "status": "ACCEPTED",
  "nextStep": "FINAL_STATUS",
  "created": "2025-05-15T07:38:56Z"
}
```

- `status` is `ACCEPTED | REJECTED | DUPLICATE_IGNORED`.
- `nextStep` is `"FINAL_STATUS"` for normal flows (wait for callback), or `"GET_AUTH_URL"` for REDIRECT_AUTH providers (poll status-check to get the `authorizationUrl`).
- `failureReason: { failureCode, failureMessage }` is set on `REJECTED`. See `references/errors.md` for the full code list.

### Failure code summary (initiation)

`NO_AUTHENTICATION, AUTHENTICATION_ERROR, AUTHORISATION_ERROR, HTTP_SIGNATURE_ERROR, INVALID_INPUT, MISSING_PARAMETER, UNSUPPORTED_PARAMETER, INVALID_PARAMETER, DUPLICATE_METADATA_FIELD, DEPOSITS_NOT_ALLOWED, INVALID_PHONE_NUMBER, INVALID_AMOUNT, AMOUNT_OUT_OF_BOUNDS, INVALID_CURRENCY, INVALID_PROVIDER, PROVIDER_TEMPORARILY_UNAVAILABLE, UNKNOWN_ERROR`.

`UNKNOWN_ERROR` (HTTP 500): **do not** assume failure. Call status-check; only treat as failed if status-check returns `NOT_FOUND`.

## Check status — GET /v2/deposits/{depositId}

### Response — 200

```json
{
  "status": "FOUND",
  "data": {
    "depositId": "afb57b93-7849-49aa-babb-4c3ccbfe3d79",
    "status": "COMPLETED",
    "amount": "100.00",
    "currency": "RWF",
    "country": "RWA",
    "payer": {
      "type": "MMO",
      "accountDetails": {
        "phoneNumber": "250783456789",
        "provider": "MTN_MOMO_RWA"
      }
    },
    "customerMessage": "Order 12345",
    "clientReferenceId": "ORD-12345",
    "created": "2025-05-15T07:38:56Z",
    "providerTransactionId": "df0e9405-fb17-42c2-a264-440c239f67ed",
    "failureReason": null,
    "metadata": { "orderId": "ORD-12345", "customerId": "customer@email.com" }
  }
}
```

- Top-level `status` is `FOUND | NOT_FOUND`.
- `data.status` is the full lifecycle enum.
- `providerTransactionId` is the MMO's own ID — useful for support tickets with the operator.
- `failureReason` populated when `data.status = FAILED`.
- `metadata` is returned as a flat object (one key per metadata entry).

`NOT_FOUND` = pawaPay never saw this depositId. Safe to mark local record as `FAILED` if it's been long enough (15+ min).

## Resend callback — POST /v2/deposits/resend-callback/{depositId}

Useful when your callback handler failed/missed an event. The deposit must be in a final state (`COMPLETED` or `FAILED`).

```json
{ "depositId": "...", "status": "ACCEPTED" }
```

Or:

```json
{
  "depositId": "...",
  "status": "REJECTED",
  "failureReason": { "failureCode": "INVALID_STATE", "failureMessage": "Deposit is still processing" }
}
```

Failure codes: `NOT_FOUND` (no such deposit), `INVALID_STATE` (not in a final status).

## The three deposit authorisation flows

The customer authorisation step varies by provider. Discover the flow type per provider from `active-conf`:

```
operationTypes.DEPOSIT.authType:  PROVIDER_AUTH | PREAUTH | REDIRECT_AUTH
operationTypes.DEPOSIT.pinPrompt: AUTOMATIC | MANUAL    (PROVIDER_AUTH only)
operationTypes.DEPOSIT.pinPromptRevivable: true|false   (PROVIDER_AUTH only)
operationTypes.DEPOSIT.pinPromptInstructions: { channels: [...] }  (when MANUAL or revivable)
operationTypes.DEPOSIT.authTokenInstructions: { channels: [...] }  (PREAUTH only)
```

### 1. PROVIDER_AUTH (the common case)

Customer receives a PIN prompt on their phone within ~5s. They enter their mobile-money PIN. Payment completes within ~20s of initiation.

- `pinPrompt: "AUTOMATIC"` — prompt arrives by itself; just show a waiting screen.
- `pinPrompt: "MANUAL"` — the customer must take an action (dial a USSD code). Show them the steps from `pinPromptInstructions`.
- `pinPromptRevivable: true` — if the prompt fails to arrive, the customer can re-trigger it (dial the code from `pinPromptInstructions`). After ~10s with no callback, show revive instructions.

Show the merchant brand on the waiting screen using `nameDisplayedToCustomer` from `active-conf` — this matches what appears on the customer's PIN prompt.

### 2. PREAUTH (currently Orange Burkina Faso)

Customer generates an OTP via the provider's USSD menu **before** the merchant initiates the deposit. The merchant collects the OTP from the customer and passes it as `preAuthorisationCode` in the initiation request.

UX:
1. Use `authTokenInstructions.channels[].instructions[language]` to show the customer the USSD steps to generate an OTP.
2. Collect the OTP from the customer in a UI input.
3. Include it as `preAuthorisationCode` when calling `/v2/deposits`.
4. The customer needs no further action — wait for the callback.

`authTokenInstructions` includes `quickLink` (a `tel:` URL with the USSD code URL-encoded) — bind it as the `href` of a button so customers on mobile can predial.

### 3. REDIRECT_AUTH (currently Wave Senegal, Wave Ivory Coast)

Customer is redirected to a provider-hosted authorisation page.

UX:
1. Include `successfulUrl` and `failedUrl` in the initiation request.
2. Response returns `"nextStep": "GET_AUTH_URL"` — the `authorizationUrl` isn't available yet.
3. **Poll** `GET /v2/deposits/{depositId}` until `data.authorizationUrl` is populated (or callback arrives with status `PROCESSING` and the URL). Usually fast (<5s).
4. Redirect the customer's browser to `authorizationUrl`. On desktop, they see a QR code to scan with the Wave app on their phone.
5. After authorising in the Wave app, the customer is redirected to your `successfulUrl` or `failedUrl`.
6. Final callback arrives with status `COMPLETED` or `FAILED`. Verify the status on your return URL by calling `GET /v2/deposits/{depositId}` — don't trust the URL choice alone.

The callback with status `PROCESSING` and `nextStep: REDIRECT_TO_AUTH_URL` is the moment to redirect. Subsequent callback with `COMPLETED` or `FAILED` is the final state.

## Recommended flow (PROVIDER_AUTH, JSON pseudocode)

```python
import uuid, requests, decimal

def initiate_deposit(token, phone_number_raw, amount_decimal, currency, msg):
    # 1. Sanitise the phone number and predict the provider.
    pred = requests.post(
        "https://api.sandbox.pawapay.io/v2/predict-provider",
        headers={"Authorization": f"Bearer {token}"},
        json={"phoneNumber": phone_number_raw}
    ).json()
    if "failureReason" in pred:
        raise ValueError(pred["failureReason"]["failureMessage"])

    # 2. Discover provider decimal support + status from active-conf.
    conf = requests.get(
        f"https://api.sandbox.pawapay.io/v2/active-conf?country={pred['country']}&operationType=DEPOSIT",
        headers={"Authorization": f"Bearer {token}"}
    ).json()
    op = next(p["currencies"][0]["operationTypes"]["DEPOSIT"]
              for c in conf["countries"]
              for p in c["providers"] if p["provider"] == pred["provider"])
    if op["status"] != "OPERATIONAL":
        raise RuntimeError(f"Provider {pred['provider']} is {op['status']}; try later")

    # 3. Round amount.
    dp = 2 if op["decimalsInAmount"] == "TWO_PLACES" else 0
    amount_str = str(amount_decimal.quantize(decimal.Decimal(10) ** -dp))

    # 4. Generate and persist depositId BEFORE the API call.
    deposit_id = str(uuid.uuid4())
    db.save(deposit_id, status="PENDING")

    # 5. Initiate.
    body = {
        "depositId": deposit_id,
        "amount": amount_str,
        "currency": currency,
        "payer": {"type": "MMO", "accountDetails": {"phoneNumber": pred["phoneNumber"], "provider": pred["provider"]}},
        "customerMessage": msg[:22],
    }
    try:
        r = requests.post(
            "https://api.sandbox.pawapay.io/v2/deposits",
            headers={"Authorization": f"Bearer {token}", "Content-Type": "application/json"},
            json=body, timeout=10
        )
    except requests.RequestException:
        # 6. Network/timeout — verify with status-check before assuming anything.
        return _verify_status(token, deposit_id)

    data = r.json()
    if data["status"] == "ACCEPTED":
        return {"depositId": deposit_id, "state": "PENDING_CALLBACK"}
    if data["status"] == "DUPLICATE_IGNORED":
        return _verify_status(token, deposit_id)
    if data["status"] == "REJECTED":
        db.update(deposit_id, status="FAILED", reason=data["failureReason"])
        return {"depositId": deposit_id, "state": "FAILED", "reason": data["failureReason"]}

def _verify_status(token, deposit_id):
    s = requests.get(
        f"https://api.sandbox.pawapay.io/v2/deposits/{deposit_id}",
        headers={"Authorization": f"Bearer {token}"}
    ).json()
    if s["status"] == "FOUND":
        return s["data"]
    if s["status"] == "NOT_FOUND":
        db.update(deposit_id, status="FAILED", reason="never_reached_pawapay")
        return {"depositId": deposit_id, "state": "FAILED"}
```

## Callback shape (deposit webhook)

Pushed by pawaPay to your configured callback URL on `COMPLETED`, `FAILED`, and (REDIRECT_AUTH only) the moment `authorizationUrl` becomes available.

```json
{
  "depositId": "afb57b93-7849-49aa-babb-4c3ccbfe3d79",
  "status": "COMPLETED",
  "amount": "100.00",
  "currency": "RWF",
  "country": "RWA",
  "payer": { "type": "MMO", "accountDetails": { "phoneNumber": "...", "provider": "..." } },
  "customerMessage": "Order 12345",
  "created": "2025-05-15T07:38:56Z",
  "providerTransactionId": "df0e9405-...",
  "failureReason": null,
  "metadata": { "orderId": "ORD-12345" }
}
```

**Note**: `clientReferenceId` is **not** included in the callback (it IS in the status-check response). If you need it, look it up locally by `depositId`.

See `references/callbacks.md` for full handler design.

## Idempotency & reconciliation

The merchant generates the `depositId` so that a retry never duplicates a payment:

- Persist the `depositId` before the initiation HTTP call.
- On network error / timeout: call `GET /v2/deposits/{depositId}`. If `FOUND`, the deposit reached pawaPay — handle accordingly. If `NOT_FOUND` and ≥15 minutes have passed, mark FAILED.
- On `DUPLICATE_IGNORED` response: the deposit is already known to pawaPay. Call status-check to learn its current state.
- Reuse of the same `depositId` for a different transaction is impossible — pawaPay rejects it. Always generate a new UUIDv4 per attempt.

See `references/errors.md` for the reconciliation cron pattern.
