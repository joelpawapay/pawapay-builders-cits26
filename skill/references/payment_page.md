# Payment Page — pawaPay-hosted checkout

Use the Payment Page when you don't want to build your own UI: pawaPay hosts a checkout page where the customer enters the phone number, picks the provider, confirms the amount, and completes the deposit. You get a `redirectUrl`, send the customer there, and receive callbacks for the resulting deposit.

The Payment Page wraps a deposit. The resulting deposit appears in the deposits API (same status-check, callbacks, refund flow) — the only difference is the customer-facing UI is pawaPay's.

## Endpoint

| Method | Path                | Purpose                | Signed? |
|--------|---------------------|------------------------|---------|
| POST   | `/v2/paymentpage`   | Create a session       | No (spec) |

The OpenAPI spec does not declare signature parameters on `/v2/paymentpage`. Signing is not required.

## Create session — POST /v2/paymentpage

### Request

```json
{
  "depositId": "afb57b93-7849-49aa-babb-4c3ccbfe3d79",
  "returnUrl": "https://merchant.com/paymentProcessed",
  "customerMessage": "Festival ticket",
  "amountDetails": { "amount": "100", "currency": "GHS" },
  "phoneNumber": "233593456789",
  "language": "EN",
  "country": "GHA",
  "reason": "Ticket to festival 2025",
  "metadata": [ { "orderId": "ORD-555" } ]
}
```

### Field reference

- `depositId` (required) — UUIDv4, generated by the merchant. Idempotency key. Persist before calling.
- `returnUrl` (required) — where to send the customer after the flow completes (success or failure).
- `customerMessage` (optional) — same 4-22 char rule as the deposit endpoint.
- `amountDetails` (optional) — `{ amount, currency }`. Locks the amount on the page. If omitted, the customer chooses.
- `phoneNumber` (optional) — locks the MSISDN on the page (customer cannot change it). Sanitised MSISDN (no `+`, no spaces, country code included).
- `language` (optional) — `EN | FR`. Defaults to the customer's browser locale.
- `country` (optional) — ISO 3166-1 alpha-3. Restricts the page to providers in this one country. **Required when `amountDetails` is supplied** (so pawaPay can render the right currency context).
- `reason` (optional, 1-50 chars) — short description shown to the customer. Different from `customerMessage` (which appears in the SMS narration).
- `metadata` (optional) — same convention as deposits.

### Field-name discrepancy

The OpenAPI spec is the authoritative source — it uses `phoneNumber` and `amountDetails.{amount,currency}`. Some public-doc examples show `msisdn` and a top-level `amount`. The spec is what the API enforces. If a request fails with `UNSUPPORTED_PARAMETER` on either field, swap to the other naming and retest in sandbox.

### Response — 200

```json
{ "redirectUrl": "https://paywith.pawapay.io/?token=eyJhbGc..." }
```

### Failure codes (initiation)

Inherits the same set as deposits — `INVALID_INPUT, MISSING_PARAMETER, INVALID_PARAMETER, UNSUPPORTED_PARAMETER, DUPLICATE_METADATA_FIELD, INVALID_CURRENCY, INVALID_PHONE_NUMBER, INVALID_PROVIDER, AMOUNT_OUT_OF_BOUNDS, INVALID_AMOUNT, AUTH/AUTHZ codes, UNKNOWN_ERROR`.

## Lifecycle

```
1. Merchant POSTs /v2/paymentpage → receives redirectUrl.
2. Customer is redirected to redirectUrl.
3. Customer enters details and presses "Pay".
4. At "Pay" press, pawaPay registers a deposit using the supplied depositId.
   — Before this point, GET /v2/deposits/{depositId} returns NOT_FOUND.
5. The standard deposit lifecycle runs (PIN prompt, REDIRECT_AUTH for Wave, etc.).
6. Customer is redirected to returnUrl.
7. Final callback to the deposit callback URL with COMPLETED or FAILED.
```

### Session validity

- The session (i.e. the `redirectUrl`) is valid for **15 minutes**.
- If the customer never presses "Pay", **no deposit is created and no callback is sent**. The `depositId` remains usable for a fresh attempt (in practice merchants generate a new ID per attempt anyway).
- After 15 minutes, the redirect URL stops working.

### Reconciliation

- After redirecting the customer, always verify the final state by calling `GET /v2/deposits/{depositId}` on your return-URL handler — don't rely on the URL alone.
- For abandoned sessions, the deposit will be `NOT_FOUND` permanently. Treat as FAILED after 15 minutes.

## Recommended flow

```python
import uuid, requests

def create_payment_page(token, base, amount, currency, country, return_url, reason):
    deposit_id = str(uuid.uuid4())
    db.save_pending(deposit_id, amount=amount, currency=currency)
    body = {
        "depositId": deposit_id,
        "returnUrl": return_url,
        "amountDetails": {"amount": str(amount), "currency": currency},
        "country": country,
        "reason": reason[:50]
    }
    r = requests.post(f"{base}/v2/paymentpage",
                      headers={"Authorization": f"Bearer {token}",
                               "Content-Type": "application/json"},
                      json=body, timeout=10).json()
    if "failureReason" in r:
        raise RuntimeError(r["failureReason"]["failureMessage"])
    return {"depositId": deposit_id, "redirectUrl": r["redirectUrl"]}

# /handlers/return-from-pawapay
def on_return(deposit_id, token, base):
    r = requests.get(f"{base}/v2/deposits/{deposit_id}",
                     headers={"Authorization": f"Bearer {token}"}).json()
    if r["status"] == "NOT_FOUND":
        return "abandoned"        # customer never pressed Pay
    return r["data"]["status"]    # COMPLETED, FAILED, PROCESSING, ...
```

## Pitfalls

- **Trusting the return URL.** A user can craft a fake return URL hit. Always re-verify the deposit state via `GET /v2/deposits/{depositId}` on landing.
- **Hardcoding `amountDetails` without `country`.** Either both or neither (pawaPay needs the country to disambiguate currency context for the page).
- **Showing the customer "payment failed" because the session expired.** No callback fires for expired sessions — your reconciliation cron is what catches them.
- **Reusing a `depositId` across attempts.** Once the customer has pressed Pay, the deposit exists. A new attempt needs a new `depositId`.
- **Skipping signature verification on the resulting deposit callback.** It's still a deposit callback — verify like any other.
