# Payouts — sending money to a customer

A payout moves funds from the merchant's pawaPay wallet to the customer's mobile money wallet. No customer authorisation is needed — the customer just receives an SMS confirmation when it lands.

## Endpoints

| Method | Path                                       | Purpose                              | Signed? |
|--------|--------------------------------------------|--------------------------------------|---------|
| POST   | `/v2/payouts`                              | Initiate a single payout             | Yes     |
| POST   | `/v2/payouts/bulk`                         | Initiate multiple payouts            | Yes     |
| GET    | `/v2/payouts/{payoutId}`                   | Check status                         | No      |
| POST   | `/v2/payouts/fail-enqueued/{payoutId}`     | Cancel an ENQUEUED payout            | No      |
| POST   | `/v2/payouts/resend-callback/{payoutId}`   | Re-trigger the final-state callback  | No      |

## State machine

```
ACCEPTED → (ENQUEUED) → PROCESSING → (IN_RECONCILIATION) → COMPLETED | FAILED
```

The `ENQUEUED` state is unique to payouts/remittances/refunds (vs deposits): when the MMO is `DELAYED`, pawaPay accepts the payout and queues it until the MMO recovers.

## Pre-flight: pick the right provider/limits

Before initiating a payout the merchant typically only has the customer's phone number. Steps:

1. **Sanitise & predict provider** via `POST /v2/predict-provider`. Use the returned `phoneNumber` (sanitised MSISDN) and the predicted `provider` going forward. Let the user override the predicted provider — it's not 100% accurate.
2. **Check the provider is enabled and operational** via `GET /v2/active-conf?country=<ISO3>&operationType=PAYOUT` — read `operationTypes.PAYOUT.status` (`OPERATIONAL | DELAYED | CLOSED`). On `CLOSED`, defer the payout. On `DELAYED`, proceed knowing it will go through `ENQUEUED`.
3. **Verify amount limits** — `operationTypes.PAYOUT.minAmount` / `maxAmount`, and round to `decimalsInAmount` (`TWO_PLACES | NONE`).

## Initiate — POST /v2/payouts

### Request

```json
{
  "payoutId": "afb57b93-7849-49aa-babb-4c3ccbfe3d79",
  "amount": "100",
  "currency": "RWF",
  "recipient": {
    "type": "MMO",
    "accountDetails": {
      "phoneNumber": "250783456789",
      "provider": "MTN_MOMO_RWA"
    }
  },
  "customerMessage": "Refund INV-555",
  "clientReferenceId": "PAYOUT-001",
  "metadata": [ { "orderId": "ORD-555" } ]
}
```

Same fields as a deposit except:

- `payoutId` (required) — UUIDv4, generated by merchant. Idempotency key.
- `recipient` (required) — same shape as `payer`, just renamed semantically.
- No `preAuthorisationCode`, no `successfulUrl`/`failedUrl`.

### Response

```json
{
  "payoutId": "afb57b93-7849-49aa-babb-4c3ccbfe3d79",
  "status": "ACCEPTED",
  "created": "2025-05-15T07:38:56Z"
}
```

`status`: `ACCEPTED | REJECTED | DUPLICATE_IGNORED`. `REJECTED` carries `failureReason: { failureCode, failureMessage }`.

### Funds reservation

On `ACCEPTED` the principal amount is reserved from the merchant's pawaPay wallet. Fees are deducted from the wallet balance only on `COMPLETED`. On `FAILED` the reservation is released back to the wallet.

This means the merchant's wallet needs to have at least `amount` available at initiation time; otherwise the payout is rejected with `PAWAPAY_WALLET_OUT_OF_FUNDS`.

### Failure code summary (initiation)

`NO_AUTHENTICATION, AUTHENTICATION_ERROR, AUTHORISATION_ERROR, HTTP_SIGNATURE_ERROR, INVALID_INPUT, MISSING_PARAMETER, UNSUPPORTED_PARAMETER, INVALID_PARAMETER, DUPLICATE_METADATA_FIELD, PAYOUTS_NOT_ALLOWED, INVALID_PHONE_NUMBER, INVALID_AMOUNT, AMOUNT_OUT_OF_BOUNDS, INVALID_CURRENCY, INVALID_PROVIDER, PROVIDER_TEMPORARILY_UNAVAILABLE, PAWAPAY_WALLET_OUT_OF_FUNDS, UNKNOWN_ERROR`.

Note: `PROVIDER_TEMPORARILY_UNAVAILABLE` happens when status = `CLOSED`. When status = `DELAYED`, the payout is `ACCEPTED` and goes `ENQUEUED` — not rejected.

## Bulk payouts — POST /v2/payouts/bulk

Same auth + signature requirements. Send an array of `PayoutInitiationRequest`. Receive an array of `PayoutCreationResponse` — each element independently `ACCEPTED | REJECTED | DUPLICATE_IGNORED`.

```json
POST /v2/payouts/bulk
[
  { "payoutId": "<uuid1>", "amount": "100", "currency": "ZMW", "recipient": {...} },
  { "payoutId": "<uuid2>", "amount": "200", "currency": "ZMW", "recipient": {...} }
]
```

Response:

```json
[
  { "payoutId": "<uuid1>", "status": "ACCEPTED",            "created": "..." },
  { "payoutId": "<uuid2>", "status": "REJECTED",            "failureReason": { "failureCode": "AMOUNT_OUT_OF_BOUNDS", ... } }
]
```

Treat each entry independently. Don't assume the whole batch succeeded.

## Check status — GET /v2/payouts/{payoutId}

```json
{
  "status": "FOUND",
  "data": {
    "payoutId": "...",
    "status": "COMPLETED",
    "amount": "100.00",
    "currency": "RWF",
    "country": "RWA",
    "recipient": { "type": "MMO", "accountDetails": { "phoneNumber": "...", "provider": "..." } },
    "customerMessage": "Refund INV-555",
    "clientReferenceId": "PAYOUT-001",
    "created": "2025-05-15T07:38:56Z",
    "providerTransactionId": "df0e9405-...",
    "failureReason": null,
    "metadata": { "orderId": "ORD-555" }
  }
}
```

Top-level `status` is `FOUND | NOT_FOUND`. `data.status`: `ACCEPTED, ENQUEUED, PROCESSING, IN_RECONCILIATION, COMPLETED, FAILED`.

## Enqueued payouts — handling MMO downtime

When the MMO is `DELAYED` in `active-conf`/`availability`:

- New payouts are still `ACCEPTED` on initiation.
- Their lifecycle status moves to `ENQUEUED`.
- pawaPay's payment operations team monitors the MMO; when it recovers, the payout is processed automatically.
- No merchant action needed; the merchant can keep showing the customer "payment in progress".

If the merchant wants to abandon an `ENQUEUED` payout:

### Cancel enqueued — POST /v2/payouts/fail-enqueued/{payoutId}

```json
{ "payoutId": "...", "status": "ACCEPTED" }
```

Or:

```json
{
  "payoutId": "...",
  "status": "REJECTED",
  "failureReason": { "failureCode": "INVALID_STATE", "failureMessage": "Payout has moved to PROCESSING" }
}
```

Failure codes: `NOT_FOUND`, `INVALID_STATE` (no longer ENQUEUED).

The cancellation is asynchronous — you'll receive a callback with `status: FAILED` and `failureReason.failureCode = MANUALLY_CANCELLED` when complete.

## Resend callback — POST /v2/payouts/resend-callback/{payoutId}

Same shape as the deposit resend-callback. Payout must be in a final state. Failure codes: `NOT_FOUND`, `INVALID_STATE`.

## Lifecycle failure codes (during processing)

Set in `failureReason.failureCode` when `data.status = FAILED`:

- `RECIPIENT_NOT_FOUND` — phone number isn't on the specified MMO.
- `WALLET_LIMIT_REACHED` — recipient wallet's transaction-limit caps hit.
- `PAWAPAY_WALLET_OUT_OF_FUNDS` — merchant wallet ran out mid-flight (rare; mostly caught at initiation).
- `MANUALLY_CANCELLED` — cancelled via fail-enqueued or the Dashboard.
- `UNSPECIFIED_FAILURE` — MMO failed but gave no reason. Retry-safe with a new ID.
- `UNKNOWN_ERROR` — pawaPay internal issue. Verify via status-check; do not assume failure.

## Callback shape (payout webhook)

```json
{
  "payoutId": "afb57b93-7849-49aa-babb-4c3ccbfe3d79",
  "status": "COMPLETED",
  "amount": "100.00",
  "currency": "RWF",
  "country": "RWA",
  "recipient": { "type": "MMO", "accountDetails": { "phoneNumber": "...", "provider": "..." } },
  "customerMessage": "Refund INV-555",

  "providerTransactionId": "df0e9405-...",
  "failureReason": null,

```

`status` in callbacks is the trimmed `CallbackStatus` enum: `COMPLETED | PROCESSING | FAILED`. `clientReferenceId` is **not** in callbacks. See `references/callbacks.md`.

## Idempotency & reconciliation

Same pattern as deposits:

1. Generate `payoutId` (UUIDv4) and persist locally before the initiation call.
2. On timeout / 5xx, call `GET /v2/payouts/{payoutId}` to verify state.
3. `DUPLICATE_IGNORED` response → call status-check to find current state.
4. Run a reconciliation cron for payouts pending > 15 minutes.

See `references/errors.md` for the full pattern.

## Sample (Node)

```javascript
import { randomUUID } from "node:crypto";
import { signRequest } from "./scripts/sign_request.js";

const BASE = process.env.PAWAPAY_BASE_URL; // https://api.sandbox.pawapay.io
const TOKEN = process.env.PAWAPAY_TOKEN;
const PRIVATE_KEY_PEM = process.env.PAWAPAY_PRIVATE_KEY;
const KEY_ID = process.env.PAWAPAY_KEY_ID;

export async function initiatePayout({ phoneNumberRaw, amountString, currency, message, country }) {
  // 1. Sanitise + predict provider.
  const predRes = await fetch(`${BASE}/v2/predict-provider`, {
    method: "POST",
    headers: { Authorization: `Bearer ${TOKEN}`, "Content-Type": "application/json" },
    body: JSON.stringify({ phoneNumber: phoneNumberRaw })
  });
  const pred = await predRes.json();
  if (pred.failureReason) throw new Error(pred.failureReason.failureMessage);

  // 2. Generate + persist ID up front.
  const payoutId = randomUUID();
  await db.payouts.insert({ payoutId, status: "PENDING" });

  // 3. Build + sign.
  const body = {
    payoutId, amount: amountString, currency,
    recipient: { type: "MMO", accountDetails: { phoneNumber: pred.phoneNumber, provider: pred.provider } },
    customerMessage: message.slice(0, 22)
  };
  const bodyBytes = Buffer.from(JSON.stringify(body));
  const signedHeaders = signRequest({
    method: "POST",
    authority: new URL(BASE).host,
    path: "/v2/payouts",
    body: bodyBytes,
    privateKeyPem: PRIVATE_KEY_PEM,
    keyId: KEY_ID
  });

  // 4. Initiate (single attempt; verify on failure).
  let res;
  try {
    res = await fetch(`${BASE}/v2/payouts`, {
      method: "POST",
      headers: { Authorization: `Bearer ${TOKEN}`, "Content-Type": "application/json", ...signedHeaders },
      body: bodyBytes,
      signal: AbortSignal.timeout(10_000)
    });
  } catch (e) {
    return await verifyPayoutStatus(payoutId);
  }
  const data = await res.json();
  if (data.status === "ACCEPTED") return { payoutId, state: "PENDING_CALLBACK" };
  if (data.status === "DUPLICATE_IGNORED") return await verifyPayoutStatus(payoutId);
  // REJECTED:
  await db.payouts.update(payoutId, { status: "FAILED", reason: data.failureReason });
  return { payoutId, state: "FAILED", reason: data.failureReason };
}

async function verifyPayoutStatus(payoutId) {
  const res = await fetch(`${BASE}/v2/payouts/${payoutId}`, {
    headers: { Authorization: `Bearer ${TOKEN}` }
  });
  const result = await res.json();
  if (result.status === "NOT_FOUND") {
    await db.payouts.update(payoutId, { status: "FAILED", reason: "never_reached_pawapay" });
    return { payoutId, state: "FAILED" };
  }
  return result.data;
}
```

## Pitfalls specific to payouts

- **Wallet pre-funding.** Payouts draw from the merchant's pawaPay wallet. The wallet must be funded (via Dashboard top-up or settlement) before payouts can land. Check `GET /v2/wallet-balances`.
- **Forgetting to handle ENQUEUED.** Don't show "failed" to the customer — show "in progress; will complete when the network recovers".
- **Retrying a `DUPLICATE_IGNORED` with a new ID.** Don't. The original payout exists. Call status-check on the original ID.
- **Bulk payouts assumed atomic.** They are not — each item resolves independently. Process the response array element by element.
